## 1. 维护前完成所有准备

1. 锁定合并后的提交 SHA，保存完整补丁、构建日志、依赖锁文件与四个镜像 digest；镜像提前构建、预载到生产主机，线上不编译。后端 `mvn -B -DskipTests package` 只用于生成已另行验证的制品。三端 `npm ci` 使用现有 lock，`npm run build` 含类型检查；移动端必须使用生产 `/mobile/` base，PC 构建保留对移动端共享源码的引用。
2. **仓库默认 `docker/backend.Dockerfile` 的基础镜像是 Java 17，不能直接用于要求保留 Java 8 的发布。** 现场只读确认现有后端镜像确实是 Java 8，并在该不可变镜像 digest 上仅替换完整 release-8 JAR。核实实际 JAR 路径，保留现有 entrypoint、JVM 参数、环境、挂载、网络及健康检查；不能凭示例猜路径或用 class 热补丁。三端同样复用现场已核验的 nginx 基础镜像/路由配置。
3. 现场只读记录真实 Compose 文件、项目名、后端及三端服务键、旧镜像 digest、环境指纹、数据库/租户、MySQL 5.7 版本、Redis 版本、JVM/JDBC 时区、当前 schema epoch/迁移记录/业务就绪状态。不要用仓库默认 Compose 覆盖现有生产配置。
4. 本次没有新 SQL 迁移，65 个既有迁移内容不变；清单纳入已有 `0703` / `0703_1`，打包 epoch 为 `2026100703`。若现场缺少应用已要求的既有迁移，先停下并按原审核增量流程处理，不能直接启动或重写 epoch。月清工具依赖 Redis 7+ 的 `PEXPIRETIME`；版本不满足时保持阻断，不在本轮顺手升级。
5. 可先运行只读月线 `preview` 评估表、租户、行数、未知对象与备份容量；运行命令和凭据管理见 [月清工具说明](../scripts/market/README-monthly-retirement.md)。预览不是停写证据，删除前必须重新预览。

## 2. 一次维护窗口内停写、备份、精确清理

1. 使用现场已有维护机制冻结新交易，停止**全部**真实/模拟采集、预热、实时引擎、补缺、历史恢复与缓存写入任务，排空或停止旧 JVM 队列；逐项记录实际服务/进程状态。不要停止或改写非目标业务数据。维护人员提供与环境指纹绑定、15 分钟内的新鲜完整停写证明。
2. 核对目标环境、数据库、表、租户和逐表候选数，完成可恢复全量相关表/触发器/缓存备份。SQL 只按 `BINARY period = BINARY '1M'` 等已准确识别的字节条件删除；JSON/缓存键精确匹配。禁止普通 `WHERE period='1M'`，禁止猜测被覆盖记录。疑似覆盖和未知表/缓存单独报告并保持阻断。
3. 生产已有触发器时，工具首次 `delete` 在保存备份与维护 SQL 后默认拒绝；**禁止工具自动生产 DDL**。永久保留此时的完整触发器库存、备份及恢复 SQL。DBA 审核并手工维护精确相关触发器后，重新 `preview`、核对新 SHA 和停写证据，正式删除使用**不同的新备份路径**；确认两份备份在删除前的表数量和内容 SHA 一致。MySQL 触发器 DDL 隐式提交，Redis 与 MySQL 不共享事务。
4. 覆盖真实源、模拟源、归档、runtime 月线子状态与全部缓存扫描；恢复存储保留无可靠月线身份的记录。核对分钟及全部非月记录数量/内容 SHA、主报价/成交量/权威版本/有效期/恢复记录保持原值；第二次删除 SQL/Redis 均应为零。缓存恢复不延长绝对期限，已过期键不复活。
5. **清理成功和失败都必须由 DBA 按首份完整库存还原所有手工移除的原触发器**，保留原定义、SQL_MODE、字符集和 collation，逐项核对定义/数量/SHA 后才可启动任何新写者。脚本只恢复它自己移除的触发器；第二份备份可能已不含手工移除的定义，`triggersRestored=true` 不证明原完整触发器已恢复。任何核对失败继续停写。

月清脚本已支持 `preview/delete/restore`，不会自动重启生产。仅本轮独占隔离容器演练可用 `--owned-trigger-maintenance`，该选项不能用于生产。若写者停写、触发器维护或身份鉴别未就绪，可在另行批准后只部署应用修复，但必须明确标记**生产月清未完成**，不能称四项完整上线验收。

## 3. 切换四个已预载镜像

保持维护状态，用现场已审核的 Compose image override 指向四个不可变 digest。只更新实际后端、PC、移动端、管理端服务；不使用 `down -v`、整套 `up --build`、全库初始化或默认配置覆盖。

```sh
# 下列变量来自现场核验；示意命令不能直接代替真实配置清单。
docker compose -f "$VERIFIED_COMPOSE" -f "$REVIEWED_IMAGE_OVERRIDE" \
  up -d --no-deps --pull never --wait \
  "$BACKEND_SERVICE" "$PC_SERVICE" "$MOBILE_SERVICE" "$ADMIN_SERVICE"
```

仅在现场 Compose 支持 `--wait` 时使用；否则使用既有健康探针。应用启动可能自动启动写者：必须按现场已有已审核机制维持维护/暂停任务，不能只假定容器启动仍然停写，也不能擅自发明配置开关。核验 schema/startup guard、健康、实际四镜像 digest、月线及别名明确拒绝、分钟线可用、0%/Home 零费用/零保证金/禁用买卖且无下单请求。达到启动与数据检查要求后，恢复已审核的新写者并解除维护。

## 4. 上线后只读验收与回滚

PC 和移动端分别连续五分钟，可并行记录。测量已配对的报价版本到**实际绘制**耗时，分别严格 **P95<3000ms**（用户本轮确认的上线阈值）；被覆盖、未配对或未绘制版本单列，不计零延迟。覆盖断线重连、WS/HTTP 交错、旧 HTTP 仅补已收盘缺口、切品种/周期、加载历史并发、小时/日/周真实 session 边界与同桶 OHLC；检查 companion conversion 与主报价版本/有效期配对。记录截图、逐版本结果及失败/未验证原因，不在只读验收中发生产订单。

若健康、数据保护或业务验收失败，重新进入维护并先停新写者。清理月线后不能直接回旧月线应用并开启写入。使用正式删除备份 `restore` 恢复数据；涉及原 INSERT/UPDATE 触发器时工具仍默认拒绝，且 `restore` 不生成触发器维护 SQL，DBA 必须从首份完整触发器库存另行审核精确维护/恢复 SQL。保持停写，人工维护相关触发器、恢复数据、再按首份完整定义还原全部原触发器，核验七表及缓存结果后才切回旧四镜像并恢复业务。新非月提交与原备份冲突时工具拒绝覆盖，保持维护人工处理。应用镜像回退与数据恢复分别记录，不能将镜像回退视为完成月线恢复。
