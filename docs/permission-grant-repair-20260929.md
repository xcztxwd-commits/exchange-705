## C1：严格替换请求

两个入口共用 `PermissionGrantInput`：

- `menuIds` 必填且必须为数组；缺字段、null、非数组均为 HTTP 400。
- 元素必须是 JSON 正整数数值，范围 `1..9223372036854775807`。字符串、布尔值、对象、数组、null、小数和指数形式均拒绝，不截断、不四舍五入、不静默过滤。即使 `1.0` 数值上为整数，也不是该接口接受的整数 token。
- 重复 ID 合并；显式 `menuIds: []` 表示清空。
- 代理 `actions` 省略或 `{}` 表示不保留任何动作；显式 null 或非对象拒绝。对象键必须为正整数菜单 ID 的十进制字符串，值必须为非空字符串元素组成的数组；单菜单的空动作数组合法。
- 未知菜单、孤立按钮、未知动作、动作不属于已选菜单、停用按钮或超出调用者权限，均不能写入。
- 全量校验通过后才替换菜单与动作，两张表仍处于同一事务。新增故障注入测试在两张表实际写入并 flush 后抛错，验证两张表都恢复到原状态。
- 角色授权参数错误现在返回 HTTP 400、`success:false`；越权仍为 HTTP 403。原先合法调用的成功响应结构不变。

## C2：管理旧授权与授予新授权分离

- `validateManagedGrants` 检查目标角色当前有效的权限，不把停用或失效的历史绑定视为一次重新授予。超级管理员可以清理历史失效绑定；普通委派管理员仍须覆盖目标全部有效能力，不能修改、删除或清空一个拥有更高有效权限的角色。
- 完全无效的历史绑定不会提高目标当前权限，因此允许其被合法清理；不存在的旧 ID 也不会阻塞修复。
- 新集合仍走严格 `validateGrant`：不存在、停用、父级失效和超出委派权限的授权都拒绝。不能借清理旧授权添加更高权限，也不能把停用权限重新写回。
- 角色改名和删除未绑定账号的角色不再因旧停用授权被卡住。超级管理员角色保护和已有账号绑定删除保护保留。
- 代理动作同步验证对应的按钮目录状态，不仅验证 `menu_action` 中有同名动作；即便调用者是超级管理员，也不能重新分配停用按钮。
