## 用户明确范围

- 截止时间为新加坡 `2026-09-01 00:00:00+08:00`，对应 UTC `2026-08-31 16:00:00`；严格删除之前的记录，不删除截止瞬间的记录。
- `user_account` 的全部原有行和字段都保留，包括截止前的用户主档。

## 实现与保护

`scripts/multitenant/hard_delete_before.py` 明确区分创建等价时间、业务周期和最后活动时间，使用实际主键选择有限记录。级联采用实际外键、已有迁移清单关系及菜单关系，包括 admin_menu.parent_id 的完整后代闭包；没有任意 `*_id` 推测。`demo_account` 只使用原始 generation=1/type=SEED 的账本建立时间。消息附件和控制任务子表按实际父创建时间处理。

历史桶必须整个周期结束才符合日期条件。资产历史基线、版本计数、任务水位、迁移协议回执及没有可信年龄的偏好/试用账户不盲删。清理最多选择 10,000 行，这不是容量测试；不生成千万条测试数据。

实际删除必须先停止并排空写入、开启数据库 read_only，生成新鲜完整备份，在不同 UUID/物理卷的标记隔离实例恢复，并核对 schema、每行所有原字段及准确十进制。在线准备快照和相同备份的双份恢复只用于演练，不冒充冻结生产恢复证明。

删除入口绑定原始用户指令、补充范围、实际源/恢复目标、源包、主键及所有原字段哈希、完整恢复证明。只在事务中先删子记录再删父记录，每个删除数量均用严格 SQL 模式的非空断言保护；数量错误、外键错误会终止连接并回滚，禁止关闭外键。不可覆盖已有 intent/result，也不盲目重试不确定的删除。

删除后证明所有用户主档字段、所有存活原字段和原 schema 保持一致；不是只比较数量或资金合计。不对余额补平，不改流水或审计来制造通过。原始备份、私有选择计划及详细证据位于受限 rollback，不提交 Git。

## 工具内存修复

原来的原字段指纹将所有逐行哈希同时返回并排序，实际行情表可占用大量客户端内存。现使用 MySQL 排序和 `--quick` 流式传输，逐行合并 SHA-256。保留原算法的排序、多重行、空表及无末尾换行语义，并拒绝未排序、未知行和中途传输失败。迁移的允许字段变换、签署默认路线、物理恢复、维护、阶段回执及 activation 保护不变。

只读检查还发现主库默认字符集/排序规则是 `latin1/latin1_swedish_ci`，模拟库则是 `utf8mb4/utf8mb4_unicode_ci`。恢复不能把两者统一成新默认值，否则触发器及存储对象的原 schema 无法准确复制。schema 指纹现在显式包括数据库默认值；只在新建空的标记隔离恢复库中先匹配实际源默认值，再导入原备份。业务源库默认值不修改，历史字段和字符字节不转换。
