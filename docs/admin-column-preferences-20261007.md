# 后台列设置刷新丢失：分析、修复与验证

日期：2026-10-07。状态：已在当前工作树修复，已完成本地 Chrome 和代码验证；未发布生产环境。

## 1. 已复现的问题

使用用户已登录的 Chrome 后台用户列表 `Users.1` 进行复现，未修改用户、订单、资金或权限数据。

- 隐藏“年收入”、调整“手机号”顺序、将“用户类型”固定在左侧；点击保存后当前页面正常。
- 保存接口 `PUT /api/admin/table-preferences/Users.1` 返回 HTTP 200 和 `{"success":true}`。
- 刷新后的 GET 也返回 HTTP 200，响应契约是**直接的 JSON 数组**，不是 `data` 或 `columns` 包装对象。

- 相同操作用于 `remark`、`email`、`id` 等英文 ID 时，刷新后保持正常。
- 所有线上复现用的列设置已恢复原值并回读确认；本次修复没有再写生产配置。

### 根因与证据边界

原 `AdminTable` 用 `column-key / prop / VNode key / label` 生成列 ID。没有字段标识的自定义列会落到中文标题。`mergeColumns` 原来只做精确 ID 匹配：乱码 ID 找不到当前列，旧设置被忽略，当前列以默认显示、默认固定位置和默认顺序补入。这形成了“保存成功，但刷新丢失”的确定链路。

生产环境的错误编码究竟发生在请求、数据库/JDBC、响应还是代理层，尚未单独定位，不能仅凭 HTTP 200 和乱码响应判定某一层有问题。本修复通过稳定英文 ID 消除对中文传输编码的依赖，并兼容已观察到的历史乱码；局部 UTF-8 声明是传输加固，不冒充已查明生产数据库根因。

此外发现两处放大问题的行为：非数组响应被静默当成“无配置”；读取完成前先渲染默认列。这些也在共享组件中修复。

## 2. 已执行的修复

### 稳定列身份，覆盖所有表格

- 审核全部 **61 个表格位置**，不更改已有 `table-key`，保留每个账号、租户、入口、表格的隔离规则。
- 为 **33 个 Vue 文件中的 116 个自定义列**增加英文 `column-key`；已有英文 `prop` 的列不变。
- 例如：`phone`、`annualIncome`、`loginLocation`、`userType`、`actions`。
- 中文标题、业务字段、操作按钮与权限检查不变。今后改标题不会改变列身份。
- 回归测试强制检查所有表格列具备 `column-key` 或 `prop`，静态标识必须是唯一的英文标识，避免新增页面再次使用中文标题作为持久化 ID。

### 兼容历史设置，不批量改数据库

`tablePreferences.ts` 在当前表格已有列范围内，生成旧中文 ID 及 UTF-8 被 Latin-1/Windows-1252 错读的别名，也覆盖已观察到的替换字符形式。

- 匹配成功后输出当前英文 ID，保留旧隐藏、固定与排序设置。
- 已存在的精确英文 ID 优先于旧别名。
- 有歧义的别名不映射，不猜测任意未知 ID，不恢复已不存在或无权限的列。
- 新增列继续使用已有的默认邻接插入逻辑，原设置不整体重置。
- 读取兼容不会自动写数据库；用户下次点击保存时写入英文 ID。不需要新增表、数据库迁移或清空历史设置。

### 读取与保存防护

- GET 必须返回合法的列配置数组；空数组表示该账号尚无配置。异常对象、字段类型、重复 ID 等明确报错并提供重试，不再冒充默认配置。
- 列配置读取完成后再显示表格，慢加载时只显示恢复状态，避免默认列闪现。
- 保存必须收到 `success === true` 才更新已保存状态、关闭窗口并提示成功。
- 网络失败或服务端拒绝时保留草稿；取消或未保存的恢复默认不覆盖服务端数据；仍禁止隐藏所有列。
- 保留现有 AbortController 和响应身份检查，迟到的旧账号响应不能覆盖新账号。

### 两套入口的 UTF-8 声明

- 普通后台列偏好 PUT 明确使用 `application/json;charset=UTF-8`。
- 独立总控只对自身列偏好路径作同样处理，不改变其他接口、凭证或会话规则。
- 两个列偏好 Controller 明确声明 UTF-8 JSON 响应；仍返回原有数组/保存确认契约。
- 更新既有浏览器测试中的错误响应包装模拟，未添加依赖。

## 3. 验证结果

### 真实 Chrome、本地真实组件

使用生产同一个 `AdminTable`，连接本地合成接口；没有连接生产业务接口。16 项检查通过：

1. 已捕获的中文乱码配置恢复隐藏、顺序、固定位置。
2. 保存只提交英文 ID，刷新前后配置完全一致。
3. 取消和未保存的恢复默认不覆盖已保存设置。
4. 不同账号隔离。
5. 不同表格隔离。
6. 普通后台和独立总控隔离。
7. 独立总控保存后刷新保持设置。
8. HTTP 200 但 `success:false` 不提示成功，保留草稿。
9. 失败保存不覆盖服务端原配置。
10. HTTP 503 保存失败提示，保留草稿。
11. 全部隐藏时拒绝保存。
12. 无效读取响应阻止表格默认闪现和覆盖。
13. 重试成功后恢复已保存配置。
14. 延迟读取期间只显示加载状态。
15. 网络记录确认旧账号延迟响应已到达，但新账号配置没有被覆盖。
16. 新标签页读取相同的服务端配置，不依赖组件内存。

### 代码与 HTTP 检查

- `npm run test:tables` 通过：真实乱码样本、旧 ID、精确优先、别名歧义、新列与删除列、可见性和固定、响应验证、保存确认、取消请求、61 个表格位置检查。
- 后端 `AdminTablePreferenceTest` 和 `ControlTablePreferenceTest` 共 7 项通过。MockMvc 使用真实 HTTP JSON 序列化/反序列化，覆盖中文和英文 ID、两种请求 Content-Type、UTF-8 响应、保存失败、账号/租户/入口隔离。仓储为测试替身，不将此结果当作生产 MySQL 编码验证。
- 普通后台与独立总控构建通过；保留既有 Sass 和大资源包警告，不做与本问题无关的打包重构。

- Git 差异检查按仓库已有 CRLF 处理：`git -c core.whitespace=blank-at-eol,blank-at-eof,space-before-tab,cr-at-eol diff --check` 通过。

## 4. 复验与发布

在 `exchange-admin` 目录运行：

```powershell
npm run test:tables
npm run dev:tables
# Chrome 打开终端输出的 127.0.0.1 地址；测试仅含模拟数据。
npm run build
npm run build:control
```

后端在不含非 ASCII 字符的工作路径运行：

```powershell
mvn "-Dtest=AdminTablePreferenceTest,ControlTablePreferenceTest" test
```

发布建议：先部署两套兼容的后端接口，再部署普通后台和独立总控前端；用具有历史列设置的账号验证“隐藏一列、移动一列、固定一列、保存、刷新”，确认 GET/PUT 的 ID 均为英文，且另一个账号和另一张表不受影响。不需要运行 SQL 或清空浏览器存储。尚未替换线上文件，因此不能宣称线上已修好。
