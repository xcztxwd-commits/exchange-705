日期：2026-09-28。版本：V3，核心业务口径已确认；实施与验收见 [实施记录](manual-history-order-verification.md)。

本版按用户最后确认的答案整理，替代 V1/V2 的执行建议。源码事实来自此前全链路核查及本次针对性复核；数据库运行状态仍是 2026-09-27 的只读快照，不代表今日数据量。本轮只分析、编写文档及验证规则算例，不实施业务代码、DDL 或资金操作。

V1 原稿保留在本地 `.bak`，不随代码提交。旧稿中的独立历史投影、全展示链标记、收益查询过滤及禁止有持仓用户入账等建议，不再作为本版实施要求。

V2 原稿同样保留在本地 `.bak`，不随代码提交。V3 取消“历史开、钱包关”的组合；不再需要给未来真实采样额外叠加虚拟收益，也不需要修改曲线实时点的金额口径。

## 1. 已确认的需求

### 1.1 订单类型

- 后台新建的是**已平仓模拟合约单**，不是期限交易订单，不经过真实撮合。
- 直接写入 `contract_order`，状态为 `CLOSED`，来源固定为 `MANUAL_TEST`。
- 开平仓时间、开平仓价格、方向、杠杆、手数、保证金、手续费及盈亏保存为订单快照。
- 不调用普通开仓后再平仓，不冻结资金，不返还从未扣过的保证金。

### 1.2 两个有依赖关系的开关

1. **将净收益添加到合约钱包**：默认关闭。开启后，当前 `CONTRACT.available` 增加此单净收益；收益为负则扣减，结果允许为负数。
2. **添加到历史权益观察值**：默认关闭。开启时必须同时开启钱包入账。历史业务调整只针对以下四张表，不作为“已实现收益查询是否计入”的控制开关：
   - `asset_history_1m`
   - `asset_history_1h`
   - `asset_history_4h`
   - `asset_history_1d`

订单保存不依赖两个开关开启。两者都关闭时，也能在用户历史仓位中看到手动订单。

仅保留三种合法组合：都关闭、只开钱包、钱包与历史都开启。开启历史时，前端自动开启钱包并说明将实际改变余额；历史未关闭前不能关闭钱包。关闭历史不自动关闭钱包，最后以确认摘要为准。后端拒绝 `history=true,wallet=false`，不能仅依赖前端，也不能收到非法组合后偷偷执行未确认的钱包入账。

### 1.3 历史调整不是孤立的一个点

用户在本轮问答中进一步明确：**平仓分钟及其后的分钟都要增加该笔收益**，不能只改 11:20 而让 11:59 保持原值。

按“增加 100”理解例子：原值为 1000 的 11:20、11:59 均变为 1100；11:20 以前的分钟不变。如果 11:59 的原值是 1050，则调整后是 1150，不是统一设为 1100。

因此，上级小时、4 小时、日汇总的受影响范围也会向后延伸，不能只改平仓所属的一行。

用户已选择包括未来新分钟。结合“历史开则钱包必须开”，实现为：既有历史回填净收益，未来正常采样自然包含本次钱包入账，不再额外叠加第二次。后续真实交易、转账、亏损或强平仍会改变权益，不把本次收益做成永远不受真实资金变化影响的固定加成。

目标分钟缺值时，向前最多回溯 24 小时，取最近的有效分钟权益；仍没有则按基础权益 0 计算。这里的“当前时间”指所选平仓分钟，不是管理员今天点击提交的时间。

### 1.4 标记与展示范围

本版只要求：

- 数据库中能识别手动订单。
- 用户历史仓位中明确显示“手动订单”，覆盖当前实际使用的 PC 和移动端历史入口。
- 后台增加新建入口及提交结果，不扩展整套展示链。

不新增资金明细、分享海报、代理业绩、交易金额、报表等处的标记，不为本功能重构这些页面。也不擅自修改这些业务对订单的统计规则。

### 1.5 负余额与强平

- 手动创建允许产生负余额；创建流程不得把负余额自动归零。
- 修复前端把负余额当成“无效账户快照”的兼容问题。
- **现有强平及强平后的清零规则不变。**
- 不再要求测试用户必须没有普通持仓或挂单；不新增独立风险池。
- 如果手动扣款影响了已有真实持仓的风险条件，后续仍可能触发现有强平并按原规则清零。这与允许创建时出现负余额并不冲突。
- 普通下单仍要求可用资金充足，不因本功能获得透支权限。

## 3. 后台交互与计算

复用现有 Element Plus，不新增 UI 库。入口放在后台订单管理的合约区域，名称为“新建已平仓模拟合约单”。

表单顺序：

1. 搜索用户 ID／邮箱，选项显示 `ID · 邮箱`；读取合约可用资金及余额版本。
2. 选择实际配置的品种，不猜测或自动替换 `BTH` 等符号。
3. 选择输入时区、开仓时间、平仓时间；显示只读历史价格及价格来源。
4. 选择做多／做空、杠杆。
5. 选择输入驱动方式：手数、仓位百分比或目标收益；其他两个值联动。
6. 选择两个效果开关，初始均关闭；开启历史自动要求钱包开启。
7. 预览实际收益、钱包调整前后余额、历史调整起点与范围；确认后创建。

滑块可以超过 100%。建议初始显示 0–200%，数字框输入更大比例时扩展滑块范围，不把 200% 当业务硬上限。超出资金的手数只提示，不拦截手动单。

可用资金小于等于 0 时，比例显示“不可计算”，禁用比例驱动，仍允许按手数或目标收益创建。不能为了显示百分比，把负余额截成 0 或用 1 充当分母。

### 3.1 用户已确认的三个口径

- 目标钱包为 `CONTRACT`，与当前可用合约资金一致，不同时给 `FUND` 加钱。
- 输入、钱包及历史调整金额使用**扣一次手续费后的净收益**；订单 `profit` 仍保存现有含义的毛盈亏，`fee` 单独保存。
- 历史价格采用分钟精度，以选定分钟的 `open` 表示该分钟起点参考价，开平仓规则一致；这不保证恰好在整分钟第 0 毫秒存在一笔成交。

例如订单毛盈利 100、手续费 10，输入框的最终收益为 90，钱包和历史同额增加 90。若输入目标净收益 100，则按扣费后接近 100 反算手数并展示步长差额。

### 3.2 公式

`A` 为当前可用合约资金，`Q` 为手数，`C` 为每手数量，`L` 为杠杆，`P0/P1` 为开平仓价格，`R0/R1` 为对应历史换算率，`F` 为每手手续费，`S` 做多取 1、做空取 -1。

```text
保证金 M = Q × C × P0 × R0 ÷ L
手续费 Fee = Q × F
毛盈亏 G = S × (P1 − P0) × Q × C × R1
净收益 N = G − Fee
仓位百分比 = (M + Fee) ÷ A × 100                 仅 A > 0 时有效

按比例反算 Q = (A × 比例 ÷ 100) ÷ (C × P0 × R0 ÷ L + F)
按净收益反算 Q = 目标净收益 ÷ [S × (P1 − P0) × C × R1 − F]
```

- 固定手数时，杠杆改变保证金，不再次放大毛盈亏。
- 反算分母为 0、结果手数非正、超出数据库精度时拒绝；不偷偷改交易方向或价格。
- 按手数步长取整后显示实际收益、实际比例与目标差额，不强行改 `profit` 凑目标值。
- 手动杠杆可突破普通上限，但仍保留正值、有限数、字段精度与运算溢出检查；普通验证不变。
- Java `BigDecimal` 做最终计算。报价、每手数量、手续费、换算率及舍入规则保存快照。
- 钱包只加 `N` 一次，`frozen` 不变，不另扣一遍手续费、不返还保证金。

## 4. 历史权益：确定后的算法

### 4.1 过去回填、未来自然采集，净收益只生效一次

设平仓所属 UTC 分钟为 `T0`，净收益为 `N`。历史开启时：

1. 当前合约钱包增加 `N` 一次。
2. 本次入账之前已经存在、且业务分钟不早于 `T0` 的有效历史值，各自增加 `N` 一次；更早分钟不变。
3. 此后新采集的分钟直接读取实际资产，不再执行 `+N`。因为钱包已实际入账，新采样已经包含这笔收益。

例如既有值都是 1000，`N=100`：昨天 11:20 以后既有记录变成 1100；实际权益入账后为 1100，则未来新分钟也为 1100。不是以后每分钟多赚 100，也不是在真实值 1100 上再加成 1200。

实时点继续使用现有真实估值。钱包和历史两个开关同时开启消除了“仅历史虚拟收益”这个分支，无需长期虚拟调整器、另一个实时资产口径或独立投影版本。

### 4.2 目标分钟缺失：最多向前找 24 小时

在添加本单 `N` 之前，按如下顺序取得基础值：

1. 目标分钟已有非空净权益，直接使用该分钟现值。
2. 目标分钟不存在或净权益为 `NULL`，在同一用户、同一口径的分钟表内查找 `[T0-24小时,T0)`，按分钟降序取第一条非空净权益。
3. 仍找不到，按用户指定的模拟规则使用基础权益 `0`。

区间包含恰好 24 小时前的分钟，不包含目标分钟之后的数据。按 UTC 实际经过 24 小时计算，夏令时不会把窗口变成 23 或 25 小时。真实 0 和负权益都是有效基础值，不能只找正数。

这是一次带索引的查询，不需要逐分钟查 1440 次。示意查询（参数均由服务器绑定）：

```sql
SELECT bucket_start, net_equity, origin
FROM asset_history_1m
WHERE user_id = :userId
  AND basis_version = 'net_equity_v1'
  AND bucket_start >= :closeMinuteMinus24h
  AND bucket_start < :closeMinute
  AND net_equity IS NOT NULL
ORDER BY bucket_start DESC
LIMIT 1;
```

例子：11:20 缺失、11:19 为空、11:18 为 800、11:17 为 1000，取 800，不取最大值，也不取 11:21 的未来值。`N=100` 时补入 11:20 的权益为 900。

24 小时内均没有有效值时：`N=100` 得到 100；`N=-100` 得到 -100。不截成 0。

此回溯规则**仅用于这笔手动单需建立基础值的平仓分钟**：不把整个缺失区间补满，不把普通采集失败自动改成 0。它也不适用于开平仓行情；缺少该分钟的价格，仍必须报错或等待数据，不能用 0 或别的分钟冒充。

### 4.3 写入顺序避免双加

在同一事务中，先读取目标分钟状态和基础值，再更新范围：

- 对所有已经存在、非空、分钟 `>=T0` 的记录统一增加 `N`，目标分钟若本来有效就包含在这一步。
- 如果目标分钟原本缺失／空值，再单独写入 `基础值 + N`。
- 不能先插入 `基础值 + N`，随后又把该行包含在整段 `+N` 中；这会把目标分钟多加一次。
- 同一分钟已有另一张手动单时，使用当前有效值继续增加本单净收益，不重置基础值，不再额外汇总一遍所有旧订单利润。
- 每次提交绑定唯一幂等键；同键同内容重试返回原结果，同键不同内容拒绝。

回溯命中的记录可能已包含之前的手动调整，这是允许的，但它作为本次基础值只能使用一次。本功能不是重演真实历史交易：基础值是按创建当时已存在的数据推定的。后续补更早订单时，对现有受影响记录增加该单增量，不重新用今天的钱包猜测过去余额。零基础、沿用基础及其来源都必须保留，不能声称恢复了未采集到的真实权益。

### 4.4 收益入账与采集必须有清楚的交接点

时间戳大小不足以证明某条观察是否已经包含钱包入账，不能只用 `observed_at < created_at` 猜测。

历史开启的提交应使用现有采集／归集锁，固定顺序取得 `equity_v1_capture`、`equity_v1_rollup`，并让订单、钱包和四表写入共用同一数据库事务：

- 事务前已完成的观察不含本次入账，执行历史回填。
- 本次提交期间不允许采集或归集夹在中间读取半成品。
- 钱包与历史一起提交之后，再释放任务锁。
- 下一次采集读取新的真实钱包，不额外加收益。

锁忙时明确返回可重试结果，不能把“没取得锁”当成功。现有 `AssetEquityStore.locked()` 自建独立连接，不能直接包在外层 JPA 事务里就当作原子操作；实施需确保 JPA/JDBC 实际共享事务连接，失败全部回滚，提交后释放命名锁。

普通资金操作通过账户行锁与版本字段处理，不能用预览时余额直接覆盖当前余额。历史关闭时不需要无谓占用历史任务锁。

### 4.5 周期按所属时间段结束判断，不按平仓后经过多久

用户已选 A。UTC 11:20 属于 11:00–12:00 小时段、08:00–12:00 四小时段、当天日时间段。到 12:00，前两个周期结束；不是等到 12:20 或 15:20。

适配当前工作区的“仅封闭归集”实现：

- 已经形成的正式旧汇总，按受影响的下级数据显式重算。
- 尚未结束的周期不制造正式汇总；后续按现有周期边界、延迟和下级完成条件归集。
- 已结束但尚在正常归集延迟内的周期不抢跑；结束不等于该秒一定已写表。
- 不恢复旧版本草稿写入，也不把遗留草稿改成当前可见数据。
- 修改旧分钟后，不能只等普通任务：其水位已经向前走，旧正式汇总需要本功能定点修复，必要时为补入的旧分钟生成对应正式上级记录，但不回退全站水位。

OHLC 根据调整后的有效下级点计算。11:00–11:19 为 1000、11:20–11:59 为 1100 时，该小时开 1000、高 1100、低 1000、收 1100。完全处于调整范围内且来源点不变的完整周期可以整体平移；边界周期及新增／修复了分钟的周期必须重算，包括极值时间和样本计数。

### 4.6 补点时间与来源不能冒充真实采样

新的模拟分钟属于 `bucket_start=T0`，真实创建时间仍是今天。它没有当时的真实观察和行情批次，不能把今天写成历史 `observed_at`，也不能编造当年的报价批次。

建议最小兼容方式：

- 分钟表增加可选的 `effective_at`，用于模拟补点的逻辑时间；新增人工补点的 `observed_at`、`quote_batch_id` 允许为空，真实采集记录不变。
- 按当前收尾快照约定，模拟分钟的逻辑时间取该分钟结束边界。`bucket_start` 仍是用户指定的平仓分钟；实际创建时间和回溯源时间分别保存。
- 分钟读取、OHLC、窗口边界、`carryIn` 和期初查询统一使用有效时间，不能有的接口取 `effective_at`，有的仍因 `observed_at=NULL` 丢掉补点。
- 保留普通记录的实际观察时间，测试新旧分钟混合时 API 时间序列不倒序。
- 现有空值行被修复时保留原观察／失败证据，追加手动估算来源，不把缺失行情伪装成当时估值成功。

实施边界建议：历史开启时，平仓分钟必须已经结束；若选择当前尚未结束分钟，提示等该分钟结束后再提交，避免提前占用未结束分钟。如果正常收尾采集随后才运行，唯一键仍须保留已经生成的人工行，不能覆盖或重复增加收益；基线写入也须识别该行来源。历史关闭时仍按普通历史时间校验处理。这是适配现有收尾采集的输入校验，不增加延迟创建任务。

### 4.7 范围与规模

- 只调整目标用户的四张历史表，保留现有 `net_equity_v1`，不建立第二套投影或发布机制。
- 已有真实记录不改钱包、债务等原始分项；另记本行手动修正额，解释净权益与原始估值之间的差额。
- 缺失补点使用 `MANUAL_CARRY` 或 `MANUAL_ZERO` 来源及估算状态，记录回溯来源、基础值、净收益、操作者和创建时间。补点参与数值与 OHLC，但不能被标成真实观察。
- 原有 `asset_history_baseline` 不作为手动回填目标；正常采集遇到已存在的人工补点时，不得误把它登记成第一条真实正权益基线。
- 只补所需目标分钟，不填满其他缺失分钟，不复制其他用户的数据。
- 预览返回受影响条数及日期范围。先实现有界、原子、可回滚的同步事务；按实际数据量验证耗时。超出验证过的处理上限应明确拒绝，不静默截断；确有大批量需求再设计分批，不先造任务平台。
- 历史缺失按 0／沿用值估算，可能与真实入账时资产产生合理差异。强制钱包开启解决的是重复计算和未来虚拟加成问题，不保证从未采集过的历史一定能与现在无缝衔接。

## 6. 最小数据及接口改造

### 6.1 数据结构建议

基于已确认口径，建议以下增量结构；此处是设计，不表示已经执行迁移：

- `contract_order.order_source`：默认 `USER`，本功能强制 `MANUAL_TEST`。
- 两个开关的创建时快照：`manual_wallet_enabled`、`manual_equity_enabled`，旧订单默认关闭。服务端强制历史开启则钱包开启。普通订单的正常收益统计不受这两个字段影响。
- 一张 `manual_order_record` 保存与订单关联的创建审计：操作者、真实操作时间、幂等键与请求摘要、选定时区、报价／计算快照、钱包增量与前后值、历史作用区间和处理结果。
- 审计增加缺值依据：`EXISTING/CARRY_24H/ZERO`、回溯源分钟、基础权益、该行原始状态、回填截止点和影响条数；用 `utf8mb4` 保存说明文本，不顺带转换全部历史表字符集。
- `asset_history_1m.manual_adjustment`：有符号 `DECIMAL(32,16)`，默认 0，记录对本行基础值的累计直接修正额。正常新采样不再增加此单修正额；真实钱包已包含收益。
- `asset_history_1m.effective_at`：可空逻辑时间，仅在需要模拟补点／估算值时间时设置。为没有真实观测的新增人工行放开 `observed_at`、`quote_batch_id` 的非空限制；普通采集仍必须提供真实时间及报价批次。
- 复用分钟表已有 `origin`、`valuation_status`、`reason_code`、`valuation_evidence` 保存来源，不伪造真实估值分项。其余三张汇总表优先复用原字段。
- 幂等键唯一，关联订单唯一；普通用户端不返回操作者等内部审计内容。

新增审计表仅服务本功能，不另外增加投影版本表、任务发布表或通用钱包账本。回溯使用分钟表已有联合主键的用户／口径／时间范围，不增加无依据的重复索引。迁移前核实实时 schema，不能导入初始全库 SQL 覆盖现有数据。

### 6.2 接口

- 用户选择和品种列表优先复用现有接口；现有后台合约查询未读取邮箱条件，不能把该查询直接当作可靠用户搜索。
- 建议 `GET /api/admin/orders/contract/manual/context?userId=...` 返回用户、合约可用余额和版本。
- 建议 `POST /api/admin/orders/contract/manual/preview` 返回历史报价状态、权威计算、回溯基础来源、预计钱包前后值、历史影响范围、未到归集时点的周期及错误原因。
- 建议 `POST /api/admin/orders/contract/manual` 提交幂等键和服务器预览凭据；客户端不能决定来源、最终价格、最终盈亏。
- 预览过期、余额或参数变化时要求重新预览，不在点击确认时偷偷换手数或入账金额。
- 只改变手数／比例时复用已查得的报价，不让拖动滑块每次都请求历史行情。

### 6.3 创建事务

1. 检查服务端内测总开关及管理员权限；普通用户接口不能调用或伪造手动参数。
2. 查询幂等结果；相同请求返回原订单，不再增加资金或历史数值。
3. 验证开关联动、预览归属、时区、开平仓时间、价格证据及数值范围。外部行情请求放在数据库资金锁之外。
4. 按固定顺序取得必要的历史任务锁、用户及资产账户锁，确认余额版本。
5. 重新计算并直接保存 `MANUAL_TEST/CLOSED`；`limit_match_enabled=false`。
6. 钱包开启时，合约账户增加扣一次手续费后的净收益；允许负数，冻结资金不动。
7. 历史开启时，在锁内重新查基础值，按照第 4 节的更新顺序处理分钟及已经到期的上级汇总，写入审计证据。与订单、钱包一起提交，任一失败全部回滚。
8. 返回订单及实际处理结果，刷新用户历史仓位；不假装尚未完成的历史更新已经完成。

权限默认建议只给内测环境的超级管理员，总开关默认关闭。关闭功能不删除旧订单的手动标记。
